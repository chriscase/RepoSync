# Capability parity map

Every capability the product has at the two epic tips, and where each option carries it. The three options render the same page content with the same markup: each page is written once and placed in each option's shell, and the build checks that the markup inside every page is identical. So a capability is either in all three or in none. What differs between options is navigation, density, type and how a page's sections are arranged, never what a person can do.

This is parity of the design. It is not evidence about the implemented product; #264 has to prove it there.

## Reading the table

- **Result** is the same for all three options and comes from the matrix row's kind.
- *existing*. Kept as it is.
- *existing, known defect*. Kept. The page draws a correction that is separate work; without it the option shows today's behaviour.
- *design proposal*. Kept, with the wording or presentation proposal in the note.
- *held or unsupported*. Shown as held or unavailable, with no control that acts.
- *needs separately owned feature work*. A gap. Drawn and marked, and not counted as parity.
- **Ledger, Console, Guide** say how that option presents it when the options differ; otherwise “same”. The link opens the first prototype page for the row.
