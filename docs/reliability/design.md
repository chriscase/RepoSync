# Phase 0 design proposal: lineage, operations, and safe upgrade

**Status:** proposed for the first review gate. This document changes no runtime or schema semantics. It covers #63, #64, and #66, and defines admission rules needed later by #65, #67–#69. The requirements in [GOAL.md](GOAL.md) and the existing issue bodies remain authoritative.

## Evidence from reviewed main

Reviewed main is `87379741779a6259f7eeb52a68cc6f061174e5ef`; a fresh remote fetch on 2026-09-23 found the same SHA. Current schema version is 12 in `crates/core/src/db/schema.rs`. Migrations are embedded SQL strings; `run_migrations` executes a migration and updates `PRAGMA user_version` separately. `commit_map` has a nullable `repo_id` added in version 6, while `git_sha` is currently NOT NULL. Repository columns, per-repository `kv_state`, global `kv_state`, and commit-map fallbacks can each supply checkpoints. The team engine pulls Git with a hard reset before checking the stored SHA, and `get_commits_since` stops at 1,000 commits even if the checkpoint has not been reached. Pair creation's `skip_import` records current tips. Import cancellation is held only in memory; setup has a cancel route, per-repository import does not. The diagnostic tests in this PR exercise the real team engine with disposable SVN/Git repositories; they are not evidence of the deployed version.

## Canonical pair identity and directional state (#63)

Define one **pair generation** as an immutable lineage record keyed by managed repository ID and a monotonic generation number. Its identity includes:

- SVN repository UUID, canonical root URL and branch-relative path, path incarnation (copy-from path/revision or explicit creation), verified source UUID/path/revision, and selected source tree at the baseline revision.
- Git provider/repository identity, full ref name, verified baseline object ID and its relation to the SVN import mapping, plus the last observed remote ref tip. Store full object IDs. A copied Git feature ref is valid when its ancestor chain reaches a verified SVN import for the same lineage and projection; an unrelated Git-first root is refused.
- Projection identity: allowed/blocked path policy and path rewrite version, plus the effective author/credential ownership policy version where it can affect emitted history. An empty policy remains the existing full-import default.

Use one authoritative logical checkpoint per `(repository ID, generation, direction)`. The SVN→Git cursor denotes the last SVN revision *examined and resolved* for that pair; the Git→SVN cursor denotes the last Git frontier *examined and resolved*. The SVN revision produced by a Git→SVN operation is recorded as that operation's effect and mapping, not as an incoming SVN cursor advance. A checkpoint can advance only in the same SQLite transaction as the resolved mapping/outcome and journal transition. No tip adoption is allowed merely because it matches an observed remote HEAD.

Mapping outcomes must be typed: `applied_and_verified`, `intentionally_filtered_no_target`, `pending`, `locally_published_not_remote`, and `unknown_reconciliation_required`. A no-target mapping has a reason/policy snapshot and a NULL target SHA or revision as appropriate. Do not make NULL and missing row synonymous. Retain source and target parents/trees or stable fingerprints sufficient to verify an external effect; commit messages and matching final trees alone are hints. Preserve all legacy rows and add scoped, generation-aware records rather than overwriting or deduplicating old rows on a guessed key.

The current physical schema is only an input to migration. An implementation may use `pair_lineages`, directional `pair_checkpoints`, and outcome rows keyed by pair/generation/source identity, with foreign keys and unique constraints. Choose exact names/DDL after inventorying real legacy shapes and #54's nullable mapping approach. Preserve numeric SVN revisions together with repository UUID and branch identity: revision 42 in two repositories is not the same source event. For a merge DAG, the Git cursor is a proven frontier, not simply whichever SHA a revwalk visited first. Unknown/unsupported DAGs block before writes.

## Legacy inventory and migration sequence (#63, coordinated with #54)

1. Identify the exact running executable/schema and quiesce all writers. Take a consistent SQLite backup including WAL, configuration, encryption key material, and local refs/workdirs; record hashes, permissions and ownership. Never start a copied installation with scheduling or outbound access. The deployed version is currently **NOT ESTABLISHED**.
2. On a copy, inventory schema version, tables/columns/indexes/foreign keys, repository IDs and hierarchy, enabled status, credentials and inheritance/rotation, settings/defaults, paths, `commit_map`, sync records, import progress, all cursor sources, and remote identities. Do not resolve a missing per-pair cursor using another pair's global maximum revision or SHA.
3. Reject a future schema version before writing. Run ordered, transactional, restart-safe changes with an exclusive single-daemon owner. The present runner's separate SQL/`user_version` writes need an atomic wrapper before any new migration is applied. Validate foreign keys and integrity after each copy. A repeated or interrupted migration must converge to the same result without duplicate rows.
4. Classify each old pair: **proven** when cursor sources, mappings, SVN UUID/path/copy ancestry, Git baseline/ref ancestry, and observed remote state agree; **ambiguous** when evidence is incomplete/conflicting; **external effect unresolved** when local records lag possible SVN/Git writes. Migrate proven pairs without altering their observed tips or valid checkpoint values. Put only ambiguous or unresolved pairs into read-safe reconciliation. Keep healthy pairs enabled and legacy disabled pairs disabled.
5. Coordinate table rebuild and NULL `git_sha` semantics with #54. Reserve mapping outcome semantics for filtered revisions without forcing a parallel incompatible `commit_map` migration. Full-import, no-policy users retain prior defaults. Do not absorb monorepo path projection implementation from #52/#60.
6. Run no-change and one-change-each-direction sync on synthetic old-code fixtures, then exercise installer/update/startup path, required key material, local refs, file permissions, and restart owner. Qualify the actual deployed version only after Chris supplies an inventory through a safe channel. No real DB or secrets are requested for Phase 0.

Before any new external effect, an old executable plus a consistent pre-upgrade snapshot can be tested as restore. After a new SVN commit or Git push, an old DB snapshot is stale: stop writers, inspect remote refs/revisions and journal, then reconcile/roll forward. A lossless down migration is not promised if new mappings would be discarded. Never reset a checkpoint to make a restore appear clean.

## Durable operations and cancellation (#64)

Use an in-process service with a SQLite operation journal and a single-daemon data-directory owner. An operation row records ID/idempotency key, authorized initiator, type, pair ID/generation, pinned SVN/Git tips and policy, phase, owner lease/instance, cancel request, timestamps, last verified checkpoint, external-effect intent/result and terminal outcome. Record intent durably before each external write. Pair and shared-target locks cover scheduler, manual sync, import, pair creation, refresh, disable/removal and restart recovery; unrelated pairs may run concurrently. The owner must be fenced so an old worker cannot mutate a newer pair generation.

Allowed transitions: `queued → running`; `queued → cancelled`; `running → cancel_requested → cancelling → cancelled` only after quiescence and effect verification; `running/cancelling → completed` when all expected effects/checkpoints verify; `running/cancelling → failed` for a known no-effect failure; and any state with an uncertain external effect → `reconciliation_required`. Recovery takes an abandoned `running`/`cancelling` operation into inspection, then resumes only proven missing steps or leaves it in reconciliation. Terminal states are immutable except an explicit new recovery operation. Status and cancel are authenticated/idempotent and target an operation ID/generation, so stale requests cannot cancel a successor. A per-repo API and UI expose request accepted, cancelling, partial work, completed/failed/reconciliation-required distinctly. Existing setup cancellation should use the same service when implemented.

Cancellation is checked before connect/export, before/after each replayed commit, batch publish, verification and final publish. Supervise child processes with deadlines, process-group termination and reap, and a bounded shutdown wait. If an external call may have succeeded as the response was lost, cancellation remains `reconciliation_required` until remote verification proves the effect. An async task abort alone is not completion. A cancelled partial import cannot enter ordinary scheduler sync as a complete pair.

For each Git push or SVN commit: persist intended source/target identities and pre-write remote state; perform the external call; query the remote again even after an error/timeout; compare exact ref parent/tree or SVN UUID/path/revision/tree and a stable operation identity backed by trusted mapping; persist verified effect and mapping/checkpoint atomically. If the DB write fails after a remote success, recovery re-reads actual remotes before any retry. Missing target, denied auth, deleted branch and uncertain history block without clone/init/reset/reimport. Notification sending is separate and must never decide checkpoint truth. No cross-SVN/Git/SQLite atomic transaction is claimed.

## Pre-replay ancestry gate (#66)

Use four distinct values: **P** is the last Git commit durably handled for this repository/pair, **O** is the previously observed remote tip if available, **R** is a freshly fetched exact configured remote branch tip, and **L** is the bridge checkout tip before inspection. `O == R` and `L == R` never establish `P == R`. For `P=A`, `L=O=R=C`, `A → B → C`, B and C remain pending. `P == R` means only the Git direction has no new commits; the SVN direction still runs. No entire-cycle early return follows from equal Git tips.

The current `do_sync_cycle` calls `fetch_svn_changes` first, and that function may adopt a revision from editable Git messages and persist it. Thus history admission must run **before** `fetch_svn_changes`, not merely before `GitClient::pull`. Inspection may fetch objects into a bounded namespace and write a scoped rejection audit/status. It must not reset the checkout, adopt any logical checkpoint, apply SVN/Git changes or write either remote. Generic finalization must retain a distinct rejection reason; a failed cycle may increment an error counter but must not report success. A successful cycle may have earlier committed effects followed by a later failure, so it cannot be represented as a known no-effect failure.

For this bounded slice, resolve P in repository scope. The repository column may contain an SVN→Git *emitted* tip while `last_git_sha_<repo_id>` still contains the earlier Git→SVN *handled* tip. The reader accepts that mismatch only when applied mappings for both tips belong to the active repository and Git ancestry proves handled→emitted; it keeps the handled tip as P. If the KV copy is absent and the column is mapped as an emitted SVN tip, the latest repository-owned applied Git→SVN mapping, or otherwise the first SVN-origin applied mapping, supplies a conservative P only when it is a full object ID and an ancestor of the emitted tip. This preserves Git work that landed before an SVN publication whose later apply failed. An unrelated or malformed copy remains blocked. A nonempty scoped KV can be a legacy source when the column is empty; no pair borrows another pair's global maximum. For legacy single-repository engines without a repository ID, global `last_git_hash` remains a compatibility source only when no competing registered repository can own it. An editable commit message is never proof of P or SVN origin. This is a temporary read path, not #63's canonical migration or lineage certificate. A long chain of mapped SVN echo commits with no KV may still hit the existing 1,000-commit gate; that legacy shape needs separate qualification rather than an unsafe cursor jump.

Fresh inspection distinguishes an absent branch, transport/auth failure, missing P object, shallow/incomplete ancestry, negative ancestry (rewrite), ambiguous legacy state, and unpublished/dirty local state. P must be an ancestor of R and the exact pending path from P to R must be selected without silently truncating at 1,000. Unqualified merge DAGs and overflow block before writes until deterministic replay is proved. An equal R and P still runs SVN processing. An unrelated local L or dirty index/worktree is blocked without destructive reset. An ordinary qualified linear path is admitted and pinned to R; subsequent checkout/reset and replay must use that same object, never a ref that may have changed after validation.

This gate contains unsafe replay but does not prove full SVN-origin lineage, distributed atomicity, exclusive ownership against another writer, or recovery after a partial external effect. Those remain #63/#64/#66 follow-up work. Never infer equivalence from a forged trailer, timestamp, short SHA, patch ID or equal-looking final tree. Normal SVN merges append revisions and mergeinfo; deletion/recreation or changed UUID/copy origin is a separate identity event. When proof is incomplete, preserve both histories and require reconciliation.

## Review 4: pinned old import, checkpoint authority and retention (#63/#64)

The fixture generator in `scripts/legacy_import_generator.rs` is a test-only driver compiled against original production crates at `87379741779a6259f7eeb52a68cc6f061174e5ef`. It calls the unchanged per-repository import route, `run_full_import` and that route's completion writer. The only source overlay is the driver. A synthetic empty Git root is created so the original route can clone its configured `main` branch; SVN revisions imported by production code follow that root and carry the actual SVN→Git mappings. The driver supplies a synthetic config file and repository credentials without assigning checkpoint values. The old writer exits before the candidate opens a byte-for-byte copy of its installation. The candidate's in-memory `data_dir` is pointed at that copy; persisted repository endpoints, branch ownership, configuration bytes and synthetic credential values are checked unchanged. A second copy is restored and polled before any new remote effect. This qualifies that pinned source version and fixture, not the unknown deployed binary.

The old-install case is compiled under the `reposync-core/reliability-fixture` test feature only in the isolated Docker runner, which packages the pinned old generator. The exact-case manifest requires its test identity and fails if it is absent or skipped. The general E2E job runs its ordinary team tests without that generator or a misleading pass for an unavailable old-code fixture.

The current-schema correction keeps three forms of handled Git evidence separate:

- An applied, repository-scoped Git→SVN row proves an outbound Git commit was applied. Its SVN revision is the effect of that direction, not an incoming SVN frontier.
- A repository-scoped SVN→Git applied row for the scoped KV cursor, at or before the repository SVN watermark, permits the old import completion cursor only under the original unfiltered path projection. The old completion writer sets both copies; a later SVN publication may update only the column. Old rows do not carry a policy identity, so a changed active path projection blocks this qualification. Full Git object IDs and handled→emitted ancestry are still required. The row alone never authorizes treating a later emitted tip as handled.
- A versioned repository/SHA/projection receipt in `kv_state` marks an intentionally handled Git commit with no SVN target. The receipt is written in the same SQLite transaction as the two Git cursor copies and the legacy global copy. Empty commits, policy-filtered commits and verified no-SVN-delta outcomes have distinct reasons. A missing or malformed receipt does not become an applied SVN row. A policy change invalidates a filtered receipt until reconciled under that policy.

For an absent KV cursor, the reader now requires a durable `handled_git_baseline_<repo>` receipt bound to a particular applied SVN→Git revision/SHA, repository and projection. A successful candidate SVN publication can create that receipt only when the pre-publication remote Git tip had no pending commits; an admitted old import with equal column/KV and a scoped applied mapping can also materialize it. It is never created from the first surviving `sync_records` row. The latest retained applied Git→SVN row, when present and descended from the baseline, can advance the handled frontier; otherwise the baseline remains the conservative frontier. Applied mapping rows remain correctness-critical and `run_maintenance(90)` prunes only old non-applied diagnostic rows. A preexisting installation whose baseline row/receipt was already pruned or cannot be verified blocks locally with `ambiguous_checkpoint`, leaving pending work and external tips intact. This is a reconciliation case, not an automatic upgrade or a checkpoint reset.

### Next permanent #63 record and old-state disposition

The next schema design should use `(repository_id, generation)` as the owner of a lineage. A generation must pin SVN UUID, root URL, branch-relative path, path incarnation/copy origin, verified baseline revision and projected tree; Git provider/repository identity, full ref and baseline object ID; and a projection/policy version. Directional handled and emitted frontiers are separate, with an explicit no-target outcome carrying source SHA/revision, reason, policy and verification. The current small receipts are compatibility proof, not a replacement for generation ownership.

| Existing state | Proposed disposition before DDL |
| --- | --- |
| Pinned old import with equal scoped column/KV, applied mapping and verified SVN/Git identities | Materialize its baseline on the copy; preserve both cursor values and configuration. The fixture proves this shape. |
| Applied outbound mapping, then SVN-emitted column / older KV | Preserve the KV handled frontier after repository mapping and ancestry checks; keep both directional meanings. |
| Current no-target receipt with matching repository, full SHA and policy | Map to an explicit no-target outcome, never to an applied remote revision. |
| Old no-target cursor lacking a receipt | Reconcile from actual policy, Git ancestry and SVN effect evidence; do not invent an applied row. |
| Absent KV with verified durable baseline and retained applied rows | Keep the conservative baseline or later proved outbound frontier. Do not select the first retained diagnostic row. |
| Absent KV with already-pruned baseline proof, conflicting copies, missing applied row, unknown Git ref or SVN identity | Read-safe `reconciliation_required` for that repository. Do not infer from row order, a message or final-tree equality. |
| Disabled repository | Preserve disabled status, endpoint/configuration and credential ownership; no automatic poll. |
| Several repositories or inherited credentials | Keep pair IDs and global/per-repository ownership separate; never borrow a global maximum. Verify each repository's source path and credential inheritance independently. |

The current `import_progress` singleton is not sufficient repository-scoped authority. Import mappings and completion cursors must agree with the actual SVN UUID/path and Git ref before a later migration marks a generation proven. Existing fixtures do not establish all copy-origin and policy shapes. Coordinate #54's nullable mapping outcome and table rebuild before any migration DDL. A migration should quiesce one writer, reject future schema versions, create a consistent WAL-aware backup with configuration and encryption-key ownership, and apply version plus data changes in one SQLite transaction. Repeated startup must be idempotent, and only proven pairs leave read-safe mode. The present runner and import completion have separate writes; this pass does not claim them atomic.

### #64 external-effect recovery contract

For one concrete SVN commit, persist operation ID, pair generation, source Git SHA/parent/tree, target SVN UUID/path and pre-write revision/tree, projection and intended SVN effect **before** the commit call. If SVN accepts the commit but the reply or local checkpoint write fails, restart with the operation in `effect_unknown`. Re-read the exact SVN target and compare UUID/path, revision ancestry, changed paths/tree and a stable operation identity against the durable intent. A message trailer or matching final tree alone is insufficient. If the effect is uniquely verified, atomically write the applied mapping, directionally correct checkpoint and terminal result. If the effect is absent with a stable pre-write target, the worker may resume the planned write. If evidence is conflicting or unavailable, keep `reconciliation_required` and prohibit a blind retry. The same rule applies to a Git push whose reply or local persistence fails: inspect the pinned remote ref parent and exact pushed object before deciding whether another push is safe. Neither a DB rollback after a remote write nor reimport is recovery.

The smallest next implementation slice is a read-only #63 inventory and generation-ownership migration proposal on additional pinned old shapes, followed by a separately reviewed transactional schema step coordinated with #54. The general #64 operation service, deployed-version qualification and active acceptance remain later gates.

## Later workflow admission (design only)

- Snapshot import (#68): pin SVN UUID/path and revision R, verify exact projected tree at R and source history boundary, then record the import Git baseline and directional cursors only after remote publication verifies. SVN advancing after R remains pending. Default full-history import is untouched.
- Late pair (#67): verify the Git branch descends from an SVN import mapping and determine the common SVN/Git baseline. Preview all pre-existing Git commits and SVN target/source changes, including parent-ahead and target-ahead cases. Existing target paths must be verified by UUID/copy ancestry and tree; never treated as equivalent solely because they exist. Conflicts require an explicit plan. A feature branch is allowed if descended from SVN origin; unrelated Git-first is refused.
- Refresh (#69): default history-preserving integration preview pins tips, policy and pair generation. Approval is specific to that plan; changed inputs invalidate it. Integration emits new SVN/Git history and verifies trees/mappings. Re-anchor is a separate gated operation preserving the old generation and displaced work; it remains unqualified until separately proved. Root DELETE continues to disable (#65); later managed removal is additive and remote deletion separate.
