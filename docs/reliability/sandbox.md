# Fixture-only reliability execution

The current #62 catalog and R01–R24 rollup live in
[`acceptance-matrix.md`](acceptance-matrix.md). Host-side honesty check:

```sh
python3 scripts/reliability-acceptance-matrix.py --self-test
python3 scripts/reliability-acceptance-matrix.py --check --report
```

That command never claims isolated SVN/Git proof. Isolated execution remains
`scripts/reliability-container.sh --all`. If Docker is unavailable the launcher
exits `NOT RUN`.

`scripts/reliability-container.sh --diagnostics` builds locked Rust test executables in a Docker build stage. The runtime image contains those executables, Git, SVN and the required-case runner; it does not contain the source checkout, `.git`, Cargo registry, host credentials or the Docker socket. The runtime uses `--network none`, a read-only image, dropped capabilities, no new privileges, a private `/fixture` tmpfs, and one fresh output directory mounted at `/evidence`. It has no host networking or production mounts. Docker is used only by the preparation launcher; the test process cannot reach its socket. If Docker is unavailable, the launcher stops with `NOT RUN`. The previous macOS `scripts/reliability-phase0.sh` is retained as a historical partial network guard and must not be used as fixture-only isolation evidence.

The runtime asserts its current directory, HOME and TMPDIR are fixture-owned. Real SVN `file://` repositories, bare Git remotes, working copies and SQLite files created by the diagnostic tests live below `/fixture/tmp`; fixture helpers verify their canonical parent is in that root before operations. The API provider listener is checked as loopback and runs in the container's isolated namespace. The runner rejects non-fixture `file://` targets, traversal and symlink escapes in synthetic admission probes. It creates a synthetic file and listener on the host outside the only bind mount, then verifies the container cannot read or write that file or reach the host listener. It also proves fixture read/write, in-namespace loopback and rejection of external egress. These are synthetic canaries; no real host secret or service is probed. The output mount is intentionally writable and should contain only generated fixture evidence. A bounded Python scanner rejects canaries, symlinks, unreadable entries and scan errors. It runs inside the container before updating the summary and on the host after container exit; CI scans the complete artifact tree before upload. Any failed scan prevents publication.

`docs/reliability/required-cases.json` lists exact named test subcases. The runner checks test discovery and requires exactly one pass and zero failures/ignored for every selected case. Mandatory IDs are also coded into the runner so deleting R09 from the manifest fails; an in-run omission self-check records this. Baseline defect observations and candidate regressions have separate tiers. A green baseline diagnostic proves its unsafe outcome was observed, not that candidate acceptance passed. The candidate cases use a real SVN-origin import, independent developer/bridge/bare-remote Git repositories, repository-owned mappings and checkpoints, and before/after state proofs. The scanner cases execute the real scanner on clean, canary and error fixtures. Scenario-wide acceptance remains separate from these subcases.

`docs/reliability/fixtures/Cargo.lock` is the recorded resolved dependency graph. The Docker build copies it to root `Cargo.lock` and uses `cargo test --workspace --no-run --locked`; no local `cargo update` step is needed. `scripts/reliability-compare.sh` archives the exact reviewed base, adds only the container harness/lock and a test-only synthetic SVN author overlay, then executes the base and candidate workspace suites with the same Dockerfile, toolchain and lock graph. It compares overlapping exact test identities and retains the known failures and ignored test in its report. The GitHub workflow uses checkout with `persist-credentials: false` and full history, builds outside the isolated runtime, and uploads fixture-only evidence for 14 days. Its pull-request `github.sha` is a synthetic merge SHA; report it separately from the feature head.

Current proof limits: the output is generated by fixtures, but this is not proof that all application paths enforce target enrollment in a normal installation. The container prevents access to host files/services by namespace and mount topology. Integrated SVN-origin API→child-engine R06, general sync-cycle cancellation, deployed-version migration, browser deletion navigation, and live acceptance remain open. Per-repository full-import cancel/reconcile is implemented and catalogued under R03/R05; that is not complete #64. The deployed version is NOT ESTABLISHED.

## Phase 0 evidence boundaries

| ID | Proven observation | Still open |
| --- | --- | --- |
| R02 | Root DELETE disables the registration while disposable SVN/Git remotes stay unchanged. | Managed removal and cleanup. |
| R03 | No-ID `POST /import/cancel` is HTTP 400; synthetic in-memory progress is unchanged. | General team-sync cancellation. Per-repository full-import cancel is catalogued under R03 in the current matrix. |
| R06 | Core fixture manually sets a child's checkpoint after SVN import; two descendant Git commits are omitted. | Real API pair creation, persisted child row and child engine in one SVN-derived fixture. |
| R08 | Separate API fixture accepts an unrelated Git-first branch and records its provider tip. | Complete lineage admission behavior. |
| R09 | Baseline replacement of an already handled Git SHA creates a further SVN revision. Candidate independent developer/bridge/bare-remote replacement and metadata-amend subcases reject before mutation with an explicit reason and zero-write assertions, including repeat/reopen. | Full reconciliation/rebase recovery and production qualification. |

The team gate uses P (handled repository cursor), O (prior observed remote tip), R (fresh pinned remote tip), and L (bridge tip). It admits a complete linear path from P to R, including L=R while P lags; P=R skips only Git-direction replay, so new SVN work still runs. It blocks uncertain state before the legacy SVN fetch can adopt a cursor. Allowed rejection effects are fetched objects and the bounded inspection ref, a repository-scoped block/status record, an audit failure and error count. The application does not yet provide distributed atomicity between inspected Git state and later publication, or a durable operation/recovery state machine.
